## 1. STATUS OF THE TC PANEL IMAGE PROBLEM — RESOLVED

**The blank TC panel image problem is no longer occurring.**

After a full CONFIG.DEFAULT + CONFIG.SAVE + REBOOT sequence performed during
this session, followed by manual re-entry of settings one at a time, the DMST
TC panel correctly displays the post-verification barcode image with VTCCP
connected and running. This has been confirmed through multiple verify cycles.

**What was confirmed via Wireshark capture (pcapng analyzed):**

- The reader pushes results to TWO simultaneous port 44444 connections
  (PC ports 55356 and 55358 — one DMST, one VTCCP)
- BOTH connections receive every push result:
  PUT /pcm_report.html, PUT /codes.xml, PUT /svg_image.img, PUT /status.xml
- DMST is NOT being starved of push data — it receives identical content to VTCCP
- The blank image was therefore NOT a data delivery problem
- Root cause was most likely a corrupted persisted parameter in the saved config
  (written by an earlier SDK Connect() call via COM.DMCC-SAVE) that caused DMST
  to suppress TC panel rendering. CONFIG.DEFAULT cleared it.

**Implication for the code:**
The LIVEIMG.MODE restore logic, SendDmccRestoreAsync, and all fix1–fix5 attempts
may be unnecessary in the current clean state. Do not re-introduce complexity
around LIVEIMG.MODE unless the problem recurs. If it does recur, the correct
diagnostic is to run DM-BaselineCompare-Enhanced.ps1 (see §5) to diff the
reader state before and after VTCCP connects.

No `[VTCCP-WRITER]` or record-commit log line appears after the validation block.
No CP window update occurs.

**Questions for Replit to answer:**

1. When VTCCP-VALID reports discrepancies, does the code still call the
   record-write path, or does it branch away (early return / throw)?

2. Where is the CP window ACK/record display triggered — before or after
   the validation check? If after, and validation aborts, the UI never updates.

3. Is there a log line (e.g. [VTCCP-WRITER] or [VTCCP-RECORD]) that should
   appear after a successful write? Its absence here suggests the write path
   is not being reached.

4. The 5 validation discrepancies — are any of them configured as blocking
   (i.e. will cause the record to be rejected rather than flagged)?
   Specifically: GNU% (37.1 push vs 0.4 HTML) is a large discrepancy and
   may be a units difference (raw vs percentage) in one of the two sources.
