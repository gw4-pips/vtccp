## The Core Problem

**DecodedData**: `011065316030393010201703209017190831`  
**SymbologyId**: `]d1` — NOT `]d2`. The DM ECC200 symbol does NOT have a FNC1 character
in first position. DMST TC's GS1 parser immediately fails with:
> *"<F1> Required at beginning of data — Application Header is Expected"*

TC's parser (by design) stops at the first failure — it never attempts to parse the AIs.
VTCCP's Command Pilot parser should do better: apply implied-FNC1 logic and attempt
best-effort AI extraction with appropriate caveats.

## GS1 Parse With Implied FNC1

The 36-character string is all ASCII digits, C40-encoded. Manual parse:

**Step 1 — AI 01 (GTIN-14, fixed 14 digits — unambiguous):**
```
AI 01  →  10653160303930
```
GTIN-14 check digit: weight sum = 90, check = (10−90 mod 10) mod 10 = **0** ✓ Valid.

**Step 2 — AI 10 (Batch/Lot, variable length — this is where FNC1 is needed):**

Remaining after GTIN: `10201703209017190831`  
After consuming AI 10 prefix: `201703209017190831` (18 chars to divide among lot + remaining AIs)

Trying each possible lot length:

| Lot value | Next position | Next AI | Remaining valid? |
|---|---|---|---|
| `20` | pos 22 | `17` → expiry `032090` → month=20 | ❌ invalid date |
| `201703` | pos 24 | `20` (Variant, 2 digits `90`), then `17` + `190831` = 2019-08-31 | ✅ |
| `2017032090` | pos 28 | `17` + `190831` = 2019-08-31 | ✅ |
| all other lengths | — | no valid AI at next position | ❌ |

**Result: TWO valid parses. String is ambiguous without FNC1.**

## ★ ANU Match — Important Data Point for GS1-2

Push XML `ANUPercent=2`, DMST HTML `ANU=2.0%` — **exact 1:1 match**.

Prior mismatches (all DM scans):
- Scan #17: push=11.5, DMST=0.1% (mismatch, factor ~115×)
- Scan #18: push=7.4, DMST=0.1% (mismatch, factor ~74×)
- Scan #20: push=59.5, DMST=0.6% (mismatch, factor ~99×)
- **Scan #21**: push=2, DMST=2.0% — **1:1 match** ← this scan

**Hypothesis**: The mismatch is NOT a simple linear scaling issue. When `raw` ANU is small
(≤ some threshold ~2–5%), push and DMST agree. When `raw` ANU is large (>7%), push is
reporting raw pixel-domain value while DMST applies a normalization that compresses the
large values dramatically. The relationship appears non-linear. This needs the
`axialNonuniformity` sub-key probe (GS1-2) to confirm.

**Key findings**:

1. **Aperture is the dominant variable for this symbol.** Aperture 16 → MOD=C (1.8 overall).
   Aperture 08 → MOD=A (overall limited by SC at 3.8). Same physical label, same firmware,
   same session. Grade difference of nearly 2 full letter grades purely from aperture selection.

2. **SC degrades with aperture 08 vs 16** (68% vs 78%). The smaller aperture
   samples fewer pixels per module, reducing the effective reflectance contrast measurement.
   Rl drops from 85→74–76; Rd stays at 7.

3. **MOD improves dramatically with aperture 08** — moves from C to A. Modulation is highly
   sensitive to aperture relative to module size. 22.8 mil at aperture 16 oversizes the
   aperture relative to the module, causing MOD degradation. Aperture 08 is better matched.

4. **Repeatability variance (both at aperture 08)**: CU=50 vs 7, MRD=40% vs 9%, NominalXDim
   18.9 vs 21.1 mil — significant positional variance between the two repeat scans.
   ErrorsCorrected=0 vs 1. This symbol is position-sensitive at aperture 08.

5. **Backlog link**: This data supports a new backlog item for aperture-selection guidance
   in VTCCP (see AP-1 in backlog). The correct aperture for a 22×22 DM with ~20 mil
   X-dimension is 08, not 16.

## Encodation Note — C40 Mode

This symbol uses C40 encoding (codeword 230). Prior DM scans used ASCII mode (or Base256).
C40 is efficient for uppercase alphanumeric + digits. For a 36-digit GS1 string, C40
packs 3 characters into 2 codewords — more efficient than ASCII (1 char per CW for digits).
VTCCP does not need to detect the encoding mode — the firmware handles it transparently.
The push XML `DecodedData` is always the decoded character string regardless of encoding mode.
