## §1. Grades and ApplicationPass behavior

**DMST report grades table**:
- ISO 15415:2011: 1.0 (D), Formal Grade = 1.0/17/660/45Q
- Custom: Fail (Quality)

**Push XML**:
- `<OverallGradeNumeric>1</OverallGradeNumeric>` / `<OverallGrade>D</OverallGrade>` ✓
- `<ApplicationStandard>Custom</ApplicationStandard>` ✓
- `<ApplicationPass>Fail (Quality)</ApplicationPass>` ✓

**ApplicationPass logic confirmed**: When ISO 15434 Data Format Check = PASS but quality grade < minimum threshold,
the aggregate `ApplicationPass` = `Fail (Quality)`. The format check result is NOT surfaced separately
in the push XML — only the aggregate result appears. This means:
- `ApplicationPass = "Fail (Quality)"` → grade failure (quality check failed, format check may have passed or been absent)
- `ApplicationPass = "Fail (Format)"` → format structure failure (anticipated; not yet captured)
- `ApplicationPass = "Pass"` → both quality and format passed
VTCCP's independent 15434 parser is the ONLY way to get field-by-field format check detail from the push channel.

## §4. DataCodewords / ECBudget / ECCapacity — still empty for live DM

**DMST report**: Data Codewords=32, Error Correction Budget=24, Errors Corrected=7, Error Capacity Used=14.
**Push XML**: `<DataCodewords></DataCodewords>`, `<ErrorCorrectionBudget></ErrorCorrectionBudget>`,
`<ErrorCapacityUsed></ErrorCapacityUsed>`, `<ErrorsCorrected>7</ErrorsCorrected>` ✓ (Corrected populated).

**Finding**: These fields are empty for live DM scans as well — this is NOT a QR or loaded-image
limitation. The push script does not have a working accessor for DataCodewords, ECBudget, or ECCapacity.
V1.25 must probe `r.trucheck.symbols[0].{dataCodewords,ecCodewords,ecCapacityUsed}` or similar.

**ErrorCapacityUsed formula confirmed** (cross-reference):
`ECCapacityUsed = ErrorsCorrected × 2` = 7 × 2 = 14 ✓ (each Reed-Solomon correction consumes 2 EC
codewords: one for error location, one for error magnitude)
`UEC% = (ECBudget − ECCapacityUsed) / ECBudget` = (24−14)/24 = 41.67% ≈ 41.7% ✓

Parser can COMPUTE ErrorCapacityUsed from ErrorsCorrected if the push field stays empty:
`ErrorCapacityUsed = ErrorsCorrected * 2` (valid for single-block RS, standard for ECC200 / QR).

## §6. Average Grade (AG) discrepancy

**DMST report**: Parameter 17 "Average Grade (AG)" = 4.0/A
**Push XML**: `<AGValue>10.2</AGValue>`, `<AGGrade>B</AGGrade>`

These disagree significantly. Cross-checking ISO 15415 mathematical expectation:
Primary parameter grades: UEC=2, SC=4, MOD=4, RM=2, ANU=1, GNU=4, FPD=4, DEC=4
Average of 8 primary grades: (2+4+4+2+1+4+4+4)/8 = 25/8 = 3.125 → Grade B (2.5–3.5)

**Push XML AGGrade=B is mathematically correct** per ISO 15415 §5 average grade computation.
**DMST report AG=4.0/A is inconsistent** with the ANU=D=1.0 result — a straight average cannot
be 4.0 when one parameter is 1.0. DMST may compute AG from a different subset (e.g., excluding
structural parameters like L-sides, QZ, TTR, TCT from the average). This needs documentation in
the parser-alignment-gap analysis (A4).

**AGValue=10.2**: The raw value 10.2 is likely a percentage from the underlying metric (possibly
the raw ANU or another optical measurement), not a grade in the 0–4 scale. The grade
letter (B) is derived from the raw value via the grading threshold table.

## §9. EncodedCharacters discrepancy

**DMST report**: Encoded characters = 38
**Push XML**: `<EncodedCharacters>33</EncodedCharacters>`

ASCII Values in DMST report confirms 38 bytes: 91 41 62 30 48 54 29 49 56 86 68 56 57 53 51 54
29 49 80 56 57 48 50 65 29 83 51 49 50 50 65 48 50 57 54 53 30 4
(38 bytes total including RS=30, GS=29, GS=29, GS=29, RS=30, EO=4 = 6 control chars)

38 − 5 = 33: push XML counts all bytes MINUS the 5 separator/structural chars (2×RS + 3×GS)
but INCLUDES EO. Or: 38 − 6 = 32 (all control chars excluded). Neither perfectly explains 33.
Most likely: the JS API's `encodedCharacters` property has its own counting convention.

**Parser note**: `<EncodedCharacters>` will not match the DMST report "Encoded characters" field.
Do not use `<EncodedCharacters>` for DMST report comparison or format validation — use
`<TotalCodewords>` instead (56 == 56 ✓, reliably consistent).

## §13. Modulation values — real optical data (live scan)

The DMST modulation table (lines 127–178 of PDF) shows 18 rows × 38 cols = 684 values ✓.
Values range 71–99 (compare: 96–99 for the pristine loaded QR image).
Notable: several `0` values in the data region (lines 145, 148, 151, 154, 157, 160, 163) — the
diagonal of zeros at module positions that indicate the worst-module locations in the lower-contrast
region. ANU grade = D (11.3% nonuniformity) — the structural distortion of this damaged symbol
is visible in the modulation grid as the column of zeros.

The zeros at module positions (row,col) correspond to the `ContrastUniformity=71 at module(12,17)`
worst-module location. Grid row 12, col 17 (0-indexed from data region) = the reported worst module.
The zero values in the modulation grid are the most-compressed modules at that location.

**B7 sheet design implication**: A "0" in the modulation grid is a meaningful data point (worst
module), not a missing value. Render as the number zero, not as empty. Use conditional formatting
in Excel to highlight low values (< 50) in red.
