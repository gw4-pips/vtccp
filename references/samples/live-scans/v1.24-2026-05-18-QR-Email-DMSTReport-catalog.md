## §1. Epoch Timestamp Bug — DMST loaded-image limitation

The DMST report header shows:
```
Verified: Wed 31-Dec-1970 07:00:00(000ms) PM
```
This is Unix epoch (timestamp=0) plus a timezone offset. The correct timestamp is
`2026-05-18T07:21:48` from the DMCC push response `<DateTime>` field.

**Implication**: For loaded-image records, VTCCP's push-derived `<DateTime>` is MORE
accurate than DMST's PDF report timestamp. VTCCP must use the push XML `<DateTime>`,
not any DMST report metadata, for loaded-image records. Flag this in the report if VTCCP
ever displays DMST report content alongside push data.

## §3. QR Matrix Size — 29×29 is the ground truth

The DMST report shows **QR Size: 29×29** (QR Version 3). The push XML shows `MatrixSize=35x35`.
The v1.24 DebugModSize probe shows `len=1369 sqrt=37 sqr=true`.

**Reconciliation**:
- 29×29 = actual QR module matrix (Version 3: 21 + (3−1)×4 = 29 modules per side) ← **ground truth**
- 37×37 = 29 + 4 quiet-zone modules each side (4-module minimum quiet zone per ISO 18004)
  = 37×37 = 1369 total ← what DebugModSize is counting (module array includes quiet zone)
- 35×35 = unexplained (possibly 37 − 1 per side from a display artifact) ← **unreliable**

Confirmed by codeword capacity:
- Total Codewords=70, Data Codewords=44, EC Budget=26
- QR Version 3 Level M: 44 data codewords + 26 EC codewords = 70 total ✓

**Parser action**: For QR records, derive version from `(MatrixSize_reported − 17) / 4 + 1`
doesn't apply to push XML's 35×35. Instead, compute from DebugModSize: `(sqrt − 8) = 37 − 8 = 29`
or from codeword count cross-reference. DMST report "QR Size" is the authoritative value
but is only available in pull-mode. Flag MatrixSize as "display only / unreliable for QR"
in the parser. A v1.25 probe of `r.trucheck.symbols[0].{rows,cols,version}` may expose the
correct version directly.

## §6. ECI field — implied vs explicit

DMST report shows **ECI: 000003** (ISO 8859-1 / Latin-1). The push AIM ID is `]Q1` (no
explicit ECI designator in the QR bitstream). ECI 000003 is the QR byte-mode default encoding
(Latin-1 is assumed when no ECI is specified per ISO 18004). This is DMST displaying the
**implied** encoding, not an actual ECI mode switch in the data.

VTCCP should NOT emit an ECI field based on push output for `]Q1` scans — it's not present.
For `]Q2` scans (explicit ECI), the ECI value is embedded in the `\000026` prefix of
DecodedData (ECI 26 = UTF-8).

## §9. Encodation Analysis — full breakdown

The QR data is encoded in three segments:
1. BYTE mode: "youareadust" (11 chars, codewords 4/11/121/111/117/97/114/101/97/100/117/115/116)
2. NUMERIC mode: "43493292" (8 chars, codeword triplets 434/932/92)
3. BYTE mode: "@gmail.com" (10 chars, starting with 4/10/64...)
4. END marker

The mode switching (BYTE → NUMERIC → BYTE) is the QR encoder's optimization for the digit
run in the email local-part. The Encodation Analysis is absent from push output and requires
the DMST report pull path or a JS API that exposes segment boundaries.

## §10. Formal Grade format for QR

Push XML: `<FormalGrade>4/A</FormalGrade>`
DMST report: `4.0/06/660/45Q` in the verification grades table

The DMST Formal Grade format is `{grade}/{aperture}/{wavelength}/{lighting}`. The push XML
`<FormalGrade>` field emits only `{grade}/{A-letter}` — not the full DMST format. The full
formal grade string for VTCCP reports should be reconstructed from push fields:
`{OverallGradeNumeric}/{ApertureRef}/{Wavelength}/{Lighting}` = `4/06/660/45Q`.
